# Architecture decisions

Append-only log. Newest at the bottom. Format: context → decision → consequences.

---

## ADR-001 — Modular monolith on Django, one container, one PostgreSQL
**Date:** 2026-09-23
**Context:** Legacy Racheeta spread logic across client apps and ad-hoc backends; cost and maintainability suffered. Owner requires low Railway cost and portability.
**Decision:** One Django project with business modules as apps. One container image serving both the API and the React build. PostgreSQL is the only stateful service. No Redis, worker, WebSocket server, search engine or PostGIS until a feature needs it.
**Consequences:** Simple operations and cheapest possible hosting. Modules must stay decoupled through clear app boundaries so that extracting one later stays possible. Insertion points for later services: cache backend (`CACHES`), `ASGI_APPLICATION`, storage backends (`STORAGES`), `INSTALLED_APPS`.

## ADR-002 — Django 5.2 LTS, Python 3.13, exact dependency pins
**Date:** 2026-09-23
**Context:** Django 6.x exists, but the project must be maintainable by rotating engineers/assistants.
**Decision:** Pin Django 5.2 LTS (supported to April 2028) and pin every dependency exactly in `requirements/*.txt` and `package-lock.json`.
**Consequences:** Predictable builds; upgrades are deliberate PRs. Revisit Django 6 after the platform is in production.

## ADR-003 — Single environment-driven settings module
**Date:** 2026-09-23
**Context:** Split `settings/dev.py` / `prod.py` files frequently drift and make it easy to run production with development settings by forgetting `DJANGO_SETTINGS_MODULE`.
**Decision:** One `config/settings.py`; behaviour switches on `DEBUG` and explicit variables. `SECRET_KEY` and `DATABASE_URL` have no defaults. `config/test_settings.py` is the only variant (fast hashing, no collectstatic).
**Consequences:** Impossible to boot without real configuration; production hardening activates automatically when `DEBUG=false`.

## ADR-004 — One `Account` model, email login, UUID primary keys
**Date:** 2026-09-23
**Context:** Legacy had multiple user types with separate identities and integer IDs leaked into clients.
**Decision:** Custom `AUTH_USER_MODEL = accounts.Account` created before any other migration. Email is the login identifier, unique case-insensitively (functional unique index on `LOWER(email)`). All domain entities use UUID v4 primary keys via `apps.core.models.BaseModel`.
**Consequences:** No username. Profiles/roles hang under the account. Public IDs are not enumerable. Composite indexes on UUIDs are slightly larger than on integers — acceptable.

## ADR-005 — Coarse primary role on the account, capabilities computed server-side
**Date:** 2026-09-23
**Context:** Many user types (doctor, nurse, hospital, pharmacy, company, real-estate…) but one identity.
**Decision:** `Account.role ∈ {PATIENT, PROVIDER, MEDICAL_COMPANY, REAL_ESTATE_SELLER, ADMIN}`. Finer typing goes into profile models (Phase 2). `/me` returns computed capability codes (`apps/accounts/roles.py`) that clients may use for UI only. `ADMIN` is never client-assignable; a DB check constraint requires `is_staff` for `ADMIN`.
**Consequences:** One place to reason about authorization. Adding a role touches `roles.py`, a migration and `PERMISSIONS.md`.

## ADR-006 — JWT with rotating, blacklisted refresh tokens
**Date:** 2026-09-23
**Context:** Web, Flutter and dashboards must share one stateless session model.
**Decision:** SimpleJWT. Access 15 min (memory), refresh 14 days (rotated on use, old token blacklisted, blacklist table in PostgreSQL). Logout blacklists the refresh token.
**Consequences:** No Redis needed for sessions. Blacklist table grows; run `flushexpiredtokens` periodically (scheduled job planned). Web stores the refresh token in `localStorage` for now — see ADR-009.

## ADR-007 — Uniform error envelope and JSON 404 under `/api/v1/`
**Date:** 2026-09-23
**Context:** Clients need one way to handle errors; DRF's default shapes vary by exception.
**Decision:** `apps.core.exceptions.api_exception_handler` wraps every DRF error as `{"error": {"code", "message", "details"?}}`. A catch-all route returns the same envelope for unknown API paths.
**Consequences:** Mobile and web share one error parser (`web/src/api/client.ts` → `ApiError`).

## ADR-008 — OpenAPI file is committed and checked in CI
**Date:** 2026-09-23
**Context:** Master plan: OpenAPI is the contract for mobile/web.
**Decision:** `docs/api/openapi.yaml` is generated by `scripts/export_openapi.sh`; CI diffs it against the code and fails when stale.
**Consequences:** Every API change is visible in review as a schema diff. Flutter/TS client generation can start from this file.

## ADR-009 — Web token storage: access in memory, refresh in localStorage (interim)
**Date:** 2026-09-23
**Context:** httpOnly-cookie refresh flows need CSRF handling and cookie-domain planning; the web app has no real pages yet.
**Decision:** Interim: refresh token in `localStorage`, access token in memory, single in-flight refresh with retry. Revisit in Phase 12 (candidate: httpOnly SameSite cookie for the refresh token + CSP).
**Consequences:** Accepted XSS exposure of the refresh token until then; no inline scripts/`dangerouslySetInnerHTML` allowed in the web app.

## ADR-010 — Django serves the React build (same origin) via WhiteNoise
**Date:** 2026-09-23
**Context:** One Railway service is the cost target.
**Decision:** Dockerfile builds `web/` and copies `dist/` into the image; `SPA_DIST_DIR` makes WhiteNoise serve assets from the URL root and a catch-all view returns `index.html` for non-API routes. In development Vite proxies `/api` and `/health` to Django, so `VITE_API_BASE_URL` stays empty everywhere.
**Consequences:** No CORS in production. If the web app is ever hosted separately (CDN), set `VITE_API_BASE_URL` and `CORS_ALLOWED_ORIGINS`; nothing else changes.

## ADR-011 — Mandatory loading pattern as shared components
**Date:** 2026-09-23
**Context:** Master plan §19: every backend-connected button/page must show loading state and block duplicate submissions.
**Decision:** `ApiActionButton`, `AsyncPage`, `LoadingOverlay`, `Spinner` and hooks `useAsyncAction` / `useAsyncData` in `web/src`. Feature code must use them instead of hand-rolled state. The Flutter app will mirror the same three components.
**Consequences:** Reviewers reject raw `<button onClick={api…}>` usage.

## ADR-012 — WSGI gunicorn now, ASGI later; migrations in the container start
**Date:** 2026-09-23
**Context:** No async views yet; Railway has no release phase.
**Decision:** Run `gunicorn config.wsgi` (2 workers). Keep `config/asgi.py`. `scripts/start.sh` runs `migrate` before serving, safe with a single replica.
**Consequences:** Switch to `uvicorn config.asgi:application` when WebSockets/async arrive. Move `migrate` to a pre-deploy step before scaling replicas.

## ADR-013 — Health endpoint does not check the database
**Date:** 2026-09-23
**Context:** Railway restarts a service whose health check fails.
**Decision:** `/health/` returns `{"status":"ok"}` if the process serves HTTP. Database problems surface as API errors and (later) monitoring, not as restart loops.
**Consequences:** Add a separate readiness/diagnostics endpoint if deeper checks are needed.

## ADR-014 — Proprietary licence, owner-assigned contributions
**Date:** 2026-09-23
**Decision:** `LICENSE` states all rights reserved by Moahaimen Talib; contributions are assigned to the owner.
**Consequences:** No open-source obligations; change only by owner decision.

## ADR-015 — Stateless HMAC tokens for password reset and email verification
**Date:** 2026-09-23
**Context:** Reset/verification links need expiring, single-use, unguessable tokens. Options: a token table with hashed values, or Django's stateless generator design.
**Decision:** Use `PasswordResetTokenGenerator` subclasses with per-purpose salts (`apps/accounts/tokens.py`). The HMAC covers a timestamp and account state (password hash / `email_verified_at` / email), so a token dies when the flow completes or the state changes. No token table.
**Consequences:** Zero storage and no cleanup job. A password reset invalidates every earlier reset link at once. Multiple verification links stay valid until one is used (accepted). Rotating `SECRET_KEY` invalidates all links (expected).

## ADR-016 — `email_verified_at` timestamp; verification does not gate features yet
**Date:** 2026-09-23
**Decision:** Replace the boolean with a nullable timestamp (data-preserving migration `accounts.0002`). Expose `email_verified` and `email_verified_at` on `/me`. No endpoint requires verification.
**Consequences:** Auditable state. Gating rules are a later, documented business decision (`PERMISSIONS.md`).

## ADR-017 — Firebase behind a verifier adapter, disabled by default
**Date:** 2026-09-23
**Context:** Owner has no Firebase credentials configured; development must not block on them.
**Decision:** `FirebaseVerifier` protocol + `DisabledVerifier` (503) + `FirebaseAdminVerifier` (lazy `firebase-admin` import, credentials file from env). Endpoint logic is fully tested with a fake verifier. Linking requires a Firebase-verified email; new accounts get an unusable password; `firebase_uid` is stored on the account.
**Consequences:** Activation is configuration only (see `AUTHENTICATION.md`). The `firebase-admin` dependency is added only when activated. A separate `SocialIdentity` table can replace `firebase_uid` if a second identity provider ever appears.

## ADR-018 — Email remains required; phone-only Firebase sign-in deferred
**Date:** 2026-09-23
**Context:** Firebase phone auth yields identities without an email, but `Account.email` is the canonical identifier.
**Decision:** The exchange rejects identities without an email (`email_required`). Supporting phone-only accounts needs a nullable email plus login/reset adjustments; decide when phone auth is actually enabled.
**Consequences:** Google sign-in works once activated; phone sign-in needs a follow-up ADR.

## ADR-019 — Email via `EMAIL_URL`; production refuses console backends
**Date:** 2026-09-23
**Decision:** Django email backend from `EMAIL_URL` (console in dev). System check `racheeta.E001` fails `manage.py check` when a console/locmem backend is configured with `DEBUG=false`. Provider choice deferred to the owner; the integration point is one variable.
**Consequences:** Tokens cannot end up in production logs by misconfiguration. CI sets a placeholder SMTP URL.

## ADR-020 — Per-request localisation of API messages
**Date:** 2026-09-23
**Decision:** `LocaleMiddleware`; clients send `Accept-Language`; the web client sends the UI language. Default `ar`.
**Consequences:** Validation messages match the UI language without client-side translation tables for backend errors.

## ADR-021 — Web session layer and route guards
**Date:** 2026-09-23
**Decision:** `react-router` (data router). One `AuthProvider` owns session state and talks to `/me`; guards (`RequireAuth`, `PublicOnly`) are the only places that check authentication; pages never read tokens. Restoration keeps tokens on non-401 failures.
**Consequences:** New protected pages are added under the `RequireAuth` group only. Feature code is reviewed against this rule.

## ADR-022 — Submit buttons are `ApiActionButton`
**Date:** 2026-09-23
**Decision:** `ApiActionButton` with `type="submit"` owns form submission (prevents native submit, works with Enter through implicit submission). Client validation failures throw `ClientValidationError`, which handlers ignore, so a failed validation never calls the backend and never shows a spinner.
**Consequences:** One loading pattern for forms and plain buttons; no `onSubmit` handlers that call the API.

## ADR-023 — One provider table, two kinds, controlled types
**Date:** 2026-09-23
**Context:** Legacy Racheeta had separate identities/tables per healthcare type. Master plan §7 asks for shared abstractions.
**Decision:** `ProviderProfile` is one table for all provider types; `ProviderType` (enum) is grouped into PRACTITIONER and FACILITY kinds. Type-specific attributes will be optional one-to-one extension tables added only when a business rule needs them. No new provider type may be added without touching the enum, migration and docs.
**Consequences:** Discovery, verification, memberships and services are written once. Extension tables must never carry authentication data.

## ADR-024 — Public discovery shows VERIFIED + visible providers only
**Date:** 2026-09-23
**Decision:** `ProviderProfile.objects.discoverable()` is the single gate for public list/detail/related lookups. Verification is admin-only; providers can request review.
**Consequences:** A fresh deployment lists nobody until administrators verify; that is the intended trust model. Ratings are absent until Phase 4 rather than faked.

## ADR-025 — Membership workflow with partial unique index
**Date:** 2026-09-23
**Decision:** `ProviderMembership` carries a status (PENDING/ACTIVE/REJECTED/ENDED) and `initiated_by`; both sides may initiate; a PostgreSQL partial unique index keeps one live row per pair while history rows remain. Full invitation UX (notifications, search-by-name) is deferred; the API foundation is complete.
**Consequences:** Phase 9 notifications can hook the transitions without schema changes.

## ADR-026 — Geography and specialties are database reference data seeded by migrations
**Date:** 2026-09-23
**Decision:** Country → Governorate → City and Specialty live in the database with stable UUIDs, bilingual names and slugs, seeded through data migrations from `seed_*.py` files. Clients fetch them from unpaginated public endpoints and never hard-code names. No PostGIS; coordinates are plain decimals.
**Consequences:** Adding a country or specialty is a migration (reviewable, reproducible). Geo search by distance is a later decision (PostGIS or bounding boxes) when the feature is scheduled.

## ADR-027 — Service prices carry a currency from an allow-list
**Date:** 2026-09-23
**Decision:** `ServiceOffering.price` (decimal ≥ 0) + `currency` (default IQD; allowed list `settings.RACHEETA["CURRENCIES"]`). No FX, no formatting on the server.
**Consequences:** Pricing for reservations (Phase 3) and payments (Phase 8) reference offerings rather than free text.

## ADR-028 — Owned design system with tokens in TypeScript and CSS custom properties
**Date:** 2026-09-23
**Context:** Phase 2.5 establishes Racheeta's permanent visual identity. Options: adopt a UI framework, or own a small system.
**Decision:** Own it: `web/src/design-system/` with tokens (TypeScript source mirrored as CSS custom properties, equality enforced by a test), CSS Modules per component, and a fixed component vocabulary (`docs/DESIGN_SYSTEM.md`). No UI framework, no utility-class framework. The former single global stylesheet is removed.
**Consequences:** Full control and no vendor churn; every new page must use design-system components, and new primitives are added to the system with a behaviour test rather than page-local variants.

## ADR-029 — Brand palette and typography
**Date:** 2026-09-23
**Decision:** Medical teal scale (600 `#1f7f77` for primary actions, 700 for brand text), charcoal `#22302f` headings, off-white `#f7f9f9` page background, semantic success/warning/error/info tokens. Font IBM Plex Sans Arabic (Arabic and Latin in one family) from Google Fonts with system fallbacks; self-hosting deferred to production hardening. Light theme only for now; role tokens make a dark theme a later, additive change.
**Consequences:** Contrast ≥ AA for text roles; no raw colours in feature CSS.

## ADR-030 — Clean-room implementation and relationship to AKAD
**Date:** 2026-09-23
**Decision:** Racheeta 2.0 copies nothing from the legacy code base (`docs/PROVENANCE.md`). It shares the owner's block-oriented design philosophy with AKAD but has its own tokens, components and identity; no AKAD files are imported.
**Consequences:** Reviews reject legacy-derived or AKAD-derived code; the design system is the reference for every future page.

## ADR-031 — Unimplemented modules are shown only as clearly marked "coming soon"
**Date:** 2026-09-23
**Decision:** The home page and footer list future modules (reservations, offers, jobs, marketplace, real estate) as non-interactive feature cards/items with a "coming soon" badge. No page uses invented data; empty states are designed instead.
**Consequences:** The product never pretends unfinished functionality exists; adding a module means replacing the badge with a real link.

## ADR-032 — Icon set is owned, not imported
**Date:** 2026-09-23
**Decision:** A single line-icon set drawn on a 24px grid lives in `design-system/icons/`; directional icons mirror in RTL. No emoji, no mixed libraries.
**Consequences:** Small bundle, consistent weight; new icons are added to `paths.tsx`.

## ADR-033 — Medical Jobs moves ahead of Reservations; Reservations stay free
**Date:** 2026-09-23
**Decision:** Phase 3 is Billing & Entitlements + Medical Jobs & Talent Marketplace; Reservations become Phase 4 and will not be gated by subscriptions.
**Consequences:** Revenue comes from employers/commercial users first. The master plan roadmap was corrected rather than rewritten.

## ADR-034 — Reusable entitlement layer keyed by capability strings
**Date:** 2026-09-23
**Decision:** `apps/billing` exposes `require / check_concurrent / consume` over capability keys for any `(subject_type, subject_id)`. Feature modules never read plans directly. Usage is consumed atomically with `select_for_update` and optional idempotency references; credits are consumed only after the plan limit.
**Consequences:** Marketplace/advertising can reuse billing unchanged. Limits are data (admin-editable), not code.

## ADR-035 — Manual subscription activation, no gateway, no seeded prices
**Date:** 2026-09-23
**Decision:** Subscriptions are requested by the owner, paid off-platform, and activated by a Super Admin with an optional minimal payment record. `Plan.price_amount` is null until the owner sets IQD prices; the web shows "price on request". Expiry is evaluated at read time (no scheduler).
**Consequences:** No PCI surface, no new infrastructure. A gateway (Phase 8) plugs into `activate_subscription`.

## ADR-036 — The structured profile is the résumé; no uploads anywhere in recruitment
**Date:** 2026-09-23
**Decision:** Job seekers describe themselves with structured children (experience, education, skills, languages, credentials). No CV files, no job attachments, no receipt uploads.
**Consequences:** No storage, no file-scanning attack surface, searchable data for talent search, snapshots are plain JSON.

## ADR-037 — Recruitment communication stays inside Racheeta
**Date:** 2026-09-23
**Decision:** Every recruitment text field is validated by `ContactLeakDetector`; jobs are re-scanned at submit and flagged for the admin; messages are text-only, immutable and scoped to an application; talent responses never contain contact or account identity.
**Consequences:** The platform keeps the recruitment value; employers reach candidates through applications, invitations and interviews.

## ADR-038 — Super Admin gates activation, verification and publication, not daily work
**Date:** 2026-09-23
**Decision:** Admin approval is required for organisation verification, subscription activation and job publication (`PENDING_ADMIN_REVIEW → PUBLISHED`). Applications, transitions, interviews, messages, invitations and talent search need no admin action. Every admin decision is audited.
**Consequences:** Trust is controlled at the entry points while the ordinary workflow stays fast.

## ADR-039 — One billable talent search = one (employer, filter signature, day)
**Date:** 2026-09-23
**Decision:** Talent search consumption is keyed by a normalised filter signature per employer per calendar day; pagination and re-ordering of the same filters are free.
**Consequences:** Employers are not punished for browsing results; the rule is documented on the page and in `JOBS.md`.

## ADR-040 — Usage references identify attempts; concurrent limits are serialised by the employer row
**Date:** 2026-09-24
**Decision:** Periodic usage (`applications.limit`, `talent.invite_limit`) is consumed with a reference that names the created record (`apply:<application id>`, `invite:<invitation id>`), never the `(job, seeker)` pair; duplicates are stopped before consumption by the one-active-record constraints. Concurrent limits (`jobs.active_limit`, `jobs.featured_limit`, `recruiter.seats`) are checked and committed under `SELECT … FOR UPDATE` on the `jobs_employer` row; `restore` uses the same gate as `submit`. Featured status is authoritative only while `featured_until > now`, normalised at read time. `request_subscription` expires elapsed ACTIVE rows itself under a billing-account row lock.
**Consequences:** Withdraw-and-reapply and re-invite are billed as new attempts; retries and races cannot double-charge or exceed a limit; no scheduler or Redis is needed. Found by the PR #4 Codex review.


## ADR-041 — Reservations use concrete slots and remain free
**Date:** 2026-09-28
**Decision:** Phase 4 reservations use concrete provider/service availability slots, transaction locking plus a partial uniqueness constraint for one live booking per slot, immutable reservation snapshots, controlled lifecycle transitions and post-commit notification hooks. Reservations do not consult billing/entitlements.
**Consequences:** Booking correctness is enforced in PostgreSQL/Django without Redis or a worker. Recurring templates and persistent notification delivery remain later additive features.

## ADR-042 — Reviews require a completed reservation and are one-per-interaction
**Date:** 2026-09-28
**Decision:** A PATIENT may review only a reservation they own whose status is COMPLETED and whose provider still resolves. `Review.reservation` is one-to-one and protected; rating is 1–5 with both serializer/model/database validation. Provider/service names are snapshotted.
**Consequences:** Ratings represent verified completed interactions rather than arbitrary public submissions. Provider aggregates are real persisted data and may be safely shown in discovery/detail.

## ADR-045 — Verified identity is frozen while review is pending or granted
**Date:** 2026-09-28
**Decision:** The identity an administrator reviews is frozen for its owner while verification is PENDING or VERIFIED, as recruitment employers already were (ADR-038): medical company `name`, `governorate`, `city`, `address`, `website`; provider `provider_type` and `specialties` (the provider type lock is extended from VERIFIED to PENDING). The check runs on the locked row inside the write's transaction and returns `identity_locked` per field; the administrator's verification decision locks the same row. Changing identity requires an administrator to move the profile back to UNVERIFIED, which removes exposure (company) or marketplace access (provider) until re-verification. Descriptive and contact fields stay editable. **VERIFIED is granted only from PENDING** (checked on the locked row): the owner's review request is what freezes the identity, so an administrator can never approve an identity that changed after the review started (UNVERIFIED/REJECTED/SUSPENDED → VERIFIED is refused with `invalid_transition`). Consumers of verified identity re-read it at query time: the marketplace catalogue re-reads the provider row and re-checks its verification, type and specialties inside the statement that returns products. **Django admin cannot bypass it:** on the provider change form `verification_status` is always read-only and an existing profile's `provider_type` and `specialties` are read-only; verification moves only through the guarded bulk actions, which call `services.set_verification` (so VERIFIED still requires PENDING), and identity changes follow the owner lifecycle (out of review via the service flow → owner edits → owner requests verification → administrator reviews). A profile's `account` is immutable after creation (read-only on the admin change form). **Ordinary writes never carry verification state:** the admin change-form save of an existing profile re-reads the row under `select_for_update()` and writes only the changed ordinary fields (`services.save_admin_form`), and the owner's PATCH runs `services.update_profile`, which locks the row, decides the identity lock there and writes only the fields the owner sent — neither performs a full save of an instance loaded before a concurrent decision, so verification status, note and timestamps written by an administrator are never rolled back.
**Consequences:** Marketplace exposure and audience targeting always rest on reviewed identity; no company can swap its verified name or domain and no provider can add a specialty to reach other audiences. There is no marketplace-specific snapshot of provider identity: the provider module's own verification is the single source.

## ADR-044 — The medical marketplace is B2B with system-controlled, category-driven audiences
**Date:** 2026-09-28
**Decision:** Phase 6 is business-to-business: verified medical companies publish products; only PROVIDER accounts with a VERIFIED provider profile browse them (public `is_visible` is not required). Categories and their audience rules (`ProductAudience`: provider type and/or specialty, never empty) are administrator reference data; a company chooses only a category, and the backend derives the audience from that category's active rules. Product payloads that carry any targeting or state field are refused. One queryset (`ProductQuerySet.targeted_for`) decides list and detail; activation re-checks the locked company and category. Product images are deferred until production media storage exists; campaigns, advertising and payments remain Phase 8.
**Consequences:** No request parameter, guessed id or company payload can expose a product to an audience the rules do not allow. Taxonomy and targeting change through the admin without code. Products have no images yet and there is no paid placement.

## ADR-043 — Offers are service-scoped snapshots with server-controlled visibility windows
**Date:** 2026-09-28
**Decision:** A provider offer must reference an owned active service at creation. Original service title/price/currency are snapshotted; offer price must be non-negative and below the original price. Public visibility requires the provider to be discoverable, the service active, `is_active=true`, and server time inside `[starts_at, ends_at)`.
**Consequences:** Clients cannot activate expired/future offers by manipulating UI state. No scheduler is required for expiry; time validity is evaluated on reads. Images remain deferred until the media/storage phase.

## ADR-046 — Medical real estate is public, seller-controlled, backend-evaluated and structured
**Date:** 2026-09-30
**Decision:** Phase 7 adds one app, `real_estate`, on the existing `REAL_ESTATE_SELLER` role (no new auth, no seller verification). (1) **Public browsing:** the catalogue is readable by anyone; "targeting" means findability through backend filters (transaction, type, place, suitable use, price, area, text), never provider-restricted audiences, ranking or paid placement (Phase 8). (2) **Seller-controlled publication:** the seller publishes and unpublishes through service endpoints; `publication_status`, `published_at` and ownership are server-owned, and one service gate (`publication_problems`) decides publication and every edit of a published listing on the resulting state. (3) **Backend-derived expiration:** `expires_at` is required and must be in the future to publish; expiry is compared with server time on every read, so there is no scheduler; an expired row stays PUBLISHED but is not public. (4) **One visibility rule:** `publicly_visible()` (PUBLISHED, unexpired, seller on an active account whose role is still `REAL_ESTATE_SELLER`, active governorate and city) serves list and detail; anything else is a plain 404. (5) **Suitability is structured:** a normalized `ListingSuitableUse` table with a unique (listing, use) constraint and a controlled code list, replaced only under the listing lock. (6) **Current-state safety:** seller and account are locked fresh in each mutation (order seller → listing → uses), so a role that changes after the request loaded the seller cannot publish. (7) **Images are deferred** until production object storage exists (as ADR-044); no upload, URL or gallery placeholder. (8) **No advertising or payment until Phase 8**, and publication never consults billing. (9) **No PostGIS** until proximity search is genuinely required; coordinates are validated decimals with database checks. Django admin is inspection-only. **Amendment (first review):** every ordinary seller mutation, drafts included, re-checks the current account state under the lock (only unpublish is exempt); the visibility rule also requires a listing's city to still belong to its governorate; the owner payload carries the current `is_active` of its geography for recovery guidance only.
**Consequences:** A seller cannot make a listing public that the gate would refuse, and cannot keep one public after losing the role, the account, its geography or its expiry; owners and the public share one authoritative rule; adding images, boosts or radius search later needs no change to these invariants.

## ADR-047 — Advertising is backend-priced sponsored product campaigns with manual payment verification
**Date:** 2026-09-30
**Decision:** (1) Phase 8 v1 is **sponsored medical-product campaigns** by `MEDICAL_COMPANY`: one campaign promotes one of the company's marketplace products to eligible providers; no other campaign types yet. (2) **Campaign targeting only narrows** Phase 6 product targeting: exposure is `ProductQuerySet.targeted_for` AND the campaign's provider-type/specialty/governorate narrowing AND payment/date state, so a campaign can never widen access. (3) **Pricing is backend-calculated** from an administrator-configured `AdvertisingRate` (days inclusive × daily rate, `Decimal`). (4) **No price is seeded**: the owner sets the business rate; without an active rate the API answers `pricing_unavailable`. (5) **The quote is snapshotted** on the campaign at submission (recomputed under the rate lock, never taken from the preview) and is immutable. (6) **Campaign payment is domain-specific** (`CampaignPayment`) and does not replace or reuse `billing.PaymentRecord`. (7) **Payment verification is manual**: an administrator confirms an off-platform payment through `verify_campaign_payment`, which activates the campaign atomically after re-checking company, product, targets and dates on locked current state. (8) **No gateway or webhook** until the owner selects a provider; `verify_campaign_payment` is the boundary a future callback will call after authenticating it. (9) **Visibility is evaluated from current state and server date** on every read (no scheduler); a paid campaign never overrides marketplace safety. (10) **No impression/click analytics** until Phase 10, and no automatic refunds (reconciliation stays manual). **Amendment (first review):** a targeted specialty must still be active to match; lifecycle actions (submit, cancel) take no client data and reject any key with `field_not_allowed`; `verify_campaign_payment` proves payment ↔ quote-snapshot coherence on the locked rows (`payment_quote_mismatch`) without consulting the current rate; rate activation is serialized by row locks in `services.save_rate` with the unique constraint as the final guard.
**Consequences:** A browser can never decide that a payment succeeded or what it costs; a campaign can be paid and still be invisible whenever the product, company or provider state says so; the payment provider and refund policy can be added later without changing these invariants.

## ADR-048 — Persistent notifications are authoritative; delivery is separate
**Date:** 2026-10-01
**Decision:** (1) **PostgreSQL is the source of truth** for notifications: a `Notification` row owned by one recipient account. Delivery channels (FCM push in Phase 9C, anything later) are best-effort additions that read the row; they never decide whether a notification exists. (2) **Creation is backend-only**, from event receivers through `services.create_notification`; there is no client create, update or delete API. Clients can only list, count, mark one read and mark all read, and those actions accept no client data (`field_not_allowed`; the server owns `read_at`). (3) **The payload is a small allow-list of safe facts** (ids, snapshotted service and provider names, start time, previous/new status); the start time is kept for future delivery/navigation but is **not rendered in notification prose** (a UTC instant with no recipient timezone would be shown wrongly; reservation pages localize it on the client); private data (patient notes, contact details, tokens, account data) is dropped at the service boundary. (4) **No prose is stored.** One presentation function maps `event_type + payload + language` to a localized title/body at read time (request language for REST; `preferred_language` for a future push), with a safe fallback for unknown events and malformed payloads. (5) **Deduplication is a database constraint** on a backend-only `dedupe_key` plus `get_or_create`, so replayed events cannot double-notify. (6) **Existing domain hooks are the integration boundary:** receivers live in `apps.notifications`, subscribe to the reservations module's post-commit signals in `AppConfig.ready()` with stable `dispatch_uid`s, and make no authorization decisions; the emitting module does not import notifications, and a receiver failure is logged without breaking the committed action. (7) **Recipients:** a new reservation notifies the provider's account; a status change notifies the other participant (never the actor; both participants when the actor is neither). (8) **No realtime infrastructure:** the web unread badge asks the backend on login, on each authenticated SPA navigation (pathname change) and after each mark-read action, with abort/stale-response protection, no polling, and the count is never computed on the client; Mark all as read is not gated on that count. (9) The resource reference is a `(resource_type, resource_id)` pair with a coherence check constraint rather than a `GenericForeignKey`; web navigation targets are derived on the client and never stored.
**Consequences:** A notification can be shown, counted and marked read without any push service, worker or broker; adding FCM later only needs to render and send an existing row; changing notification wording needs no migration; a replayed or duplicated event cannot produce a second notification; rolled-back business actions never notify.



## ADR-049 — Generic chat is context-authorized; reservation chat uses observed sequence read cursors
**Date:** 2026-10-02
**Decision:** (1) Phase 9B introduces generic `Conversation`, `ConversationParticipant` and immutable text-only `Message` rows, but a generic schema does **not** imply generic public messaging. The only conversation creation context in 9B is an existing Reservation. The backend locks that reservation and derives the two participants from `Reservation.patient` and `ProviderProfile.account`; clients never submit participant account IDs. One database unique constraint permits one conversation per context. (2) Conversation/message reads and writes are participant-scoped and foreign/nonexistent IDs disclose the same 404; there is no arbitrary conversation-create, message-update or message-delete application API, and Django admin is inspection-only. (3) Messages receive a monotonically increasing per-conversation sequence under a conversation row lock. Read state is a participant cursor, `last_read_sequence`. A read receipt submits `through_sequence`, the highest sequence the client actually rendered; the server locks the conversation, refuses a cursor beyond current `last_sequence`, and advances monotonically only to the submitted value. Therefore a message that arrives after rendering cannot be accidentally marked read. (4) Page 1 is the latest message slice, returned chronologically inside that slice; list/history use normal bounded pagination. (5) Existing application-scoped `RecruitmentMessage` remains untouched and retains its recruitment-specific authorization/moderation. (6) No FCM, WebSockets, Redis, Celery or worker is added in 9B. The database is authoritative; push belongs to 9C and realtime remains optional.
**Consequences:** The data model can support future deliberately authorized contexts without opening user-to-user messaging. Reservation participants can communicate now with bounded REST APIs and race-safe unread state. Adding another context later requires an explicit backend authorization resolver, not a client-supplied participant list. Recruitment behavior cannot regress through an implicit migration.

## ADR-050 — FCM push is a best-effort delivery layer over authoritative PostgreSQL state
**Date:** 2026-10-02
**Decision:** (1) Push never decides whether a notification or message exists; `Notification` / `Message` rows stay authoritative and FCM success is not recorded as state. (2) **Delivery registration is separate:** `PushDevice` stores one FCM token with one owning account; the token is **globally unique** (database constraint) and registration under another account **transfers** it, so account switching cannot leak the previous user's pushes; ownership is always `request.user`. Platforms are a bounded set (`ANDROID`, `IOS`, `WEB`), at most 10 active devices per account, no device fingerprinting. (3) **Firebase sits behind `apps.notifications.push.PushSender`** (`DisabledPushSender` default; `FirebaseAdminPushSender` reusing `FIREBASE_CREDENTIALS_FILE`); the rest of the code calls `push_service`. (4) **After commit, never raising:** triggers use `transaction.on_commit`; `deliver` swallows and logs (no full tokens), so Firebase outages cannot fail or roll back a business action. No worker/queue infrastructure is introduced; fan-out is bounded (≤10 devices). **`on_commit` is not asynchronous**, so the latency of delivery is the originating request's latency and is bounded explicitly (see the amendment). (5) **Only permanent rejections** (`UnregisteredError`, `SenderIdMismatchError`) deactivate a device; all else is transient. (6) **Triggers:** newly created persistent notifications (replays do not repush; Phase 9A recipient rules and self-notification suppression are inherited) and new chat messages via a post-commit `message_sent` signal handled in the notifications module (other participant only; read cursors untouched). (7) **Privacy:** generic localized lock-screen text, ids only in `data`, push data never authorizes. (8) Web/mobile token acquisition is deferred (no Firebase client or service worker in the repo; mobile not started).
**Consequences:** A push outage degrades to "open the app to see it"; a token can never serve two accounts; a future worker or realtime transport can replace inline delivery without touching domain code.

**Amendment (acceptance review, P2 — fan-out latency):** the first implementation sent to each device sequentially with a per-device timeout, so a Firebase hang could hold the request for devices × timeout (~50 s). Now: (a) `PushSender` exposes one operation, `send_batch(tokens, message)`, and `push_service.deliver` makes exactly one call per delivery; (b) `FirebaseAdminPushSender` uses `messaging.send_each_for_multicast` (firebase-admin 7.7.0 sends the tokens concurrently on its own pool; per-token results come back as `BatchResponse.responses[i]`); (c) because the SDK's timeout is per socket operation and its retry policy is not configurable (measured: a hung server 2× the timeout, a 503 storm ~7 s, token refresh up to 120 s), the call runs under a **hard caller-side deadline** (3 s) on a fixed pool with a **bulkhead** (≤4 batches in flight per process; a batch holds its slot until it really finishes) and a **fail-fast window** (10 s after a missed deadline); an abandoned call finishes in the background and its result is discarded; (d) a refused, timed-out or failed batch keeps every registration; only per-token `UnregisteredError`/`SenderIdMismatchError` deactivate; a response whose length does not match the tokens is never trusted. No Redis, Celery, queue or per-request thread spawning is introduced; the pool threads never touch the database.

## ADR-051 — Dashboards are server-scoped aggregates over existing records, not a new data store
**Date:** 2026-10-02
**Decision:** (1) Phase 10 adds a model-less app, `apps.dashboards`, with **no migration and no table**: every number is computed by PostgreSQL from authoritative rows at request time (no cache, no snapshot table, no Redis/Celery/Elasticsearch). (2) **One small endpoint per dashboard** under `/api/v1/dashboards/` (patient, doctor, facility, company, recruiter, admin) plus an index; there is no endpoint that returns every organisation's data. Each is `GET`, read-only and **parameterless**: ownership comes only from the signed-in account's current database state (profile, company, active membership, staff flag), never from a client id. (3) **One source of truth for access**: `access.py` backs both the permission classes and the index (`GET /dashboards/`), and the web hub renders only what the server lists. (4) **Reuse, do not rebuild:** the company dashboard composes `marketplace.services.dashboard_summary` and `advertising.services.dashboard_summary` (adding only payment status), and the real-estate owner dashboard is the existing endpoint called directly; the new OpenAPI component is named `MedicalCompanyDashboard` so it cannot shadow the existing `CompanyDashboard`. (5) **Aggregation discipline:** conditional aggregates in one statement per block with `.order_by()` to clear default ordering, zero-filled status maps, bounded lists (≤ 5), explicit column allow-lists for rows, and declared response serializers so an undeclared field can never leave the server; query-count tests pin both constancy against data volume and the per-endpoint total. (6) **Only metrics backed by real data:** no revenue, views, impressions, conversions or trends; deferred metrics are listed with reasons in `DASHBOARDS.md`. A facility never aggregates its practitioners' reservations because no authoritative relation exists. (7) **Entitlement honesty:** recruiter applicant aggregates follow the existing applicant-read gate and are `null` with a machine-readable reason (`organization_not_verified`, `plan_required`) when withheld, never silently zero; "no reviews" is `null`, not 0. (8) **Administrator dashboard is counts only**, uses the existing staff authorization, selects no personal field, and offers no mutation; reads are not audited, consistent with the existing admin list endpoints. (9) **Web:** one `/dashboard` route under `RequireAuth`; the page is keyed by account id so a previous account's late response is never shown, only the selected dashboard loads, nothing polls, and existing design-system components and i18n groups are reused.
**Consequences:** Dashboards cannot drift from the domain data, add no write path and no infrastructure, and remain correct when a membership, profile or entitlement changes (the next request sees it). Adding a metric requires an authoritative source and a contract update; trend charts or revenue need new data capture first.

## ADR-053 — Mobile session lifecycle
**Date:** 2026-10-03
**Decision:** (1) The backend remains the only authentication authority (JWT, rotating refresh); the app adds no second authority and no Firebase login. (2) **Access token: memory only. Refresh token: secure storage**, rewritten on every rotation *before* use (the old one is already blacklisted). (3) **Refresh is single flight** in `SessionCore`: N concurrent 401s cause one `/auth/refresh`; a request whose token was already rotated retries without refreshing again. (4) **Definitive vs transient failure:** 401/403/400/404 from refresh end the session (storage cleared, state `Anonymous(expired)`); network, timeout, 5xx and 429 keep the session. At start-up a transient failure shows a retry screen (credentials kept) rather than logging out. (5) **Stale-response protection in three layers:** a `SessionScope` per session cancels its in-flight HTTP requests when it ends; `ApiClient` rejects results whose scope generation changed; `SessionController` tickets drop superseded restore/login/`/me` results. A previous account's data can never populate the UI after logout or account switching. (6) **Logout is local-first:** state and storage are cleared (with one retry) before the best-effort `/auth/logout`; server failure or "already revoked" never keeps the user signed in. (7) `/me` is canonical for identity, role and permission codes; navigation availability derives from it and only decides what is *shown*. (8) FCM device registration is out of scope until 11E.
**Consequences:** An attacker with filesystem access gets at most a refresh token that the platform keystore protects; a lost network never silently signs the user out; the session logic is pure Dart and fully unit-tested without a UI.

## ADR-054 — Mobile patient flows: backend-authoritative, account-scoped, explicit time policy
**Date:** 2026-10-03
**Decision:** (1) **The backend decides.** Availability is a snapshot, booking and cancellation answers are final; the app generates no slots, derives no eligibility beyond a UI hint (*Cancel* offered from status + start time, since the API has no `can_cancel`), and invents no endpoint, field or status. (2) **Timezone policy:** timestamps must carry an explicit offset or the response is rejected; instants are UTC internally and on the wire; the device's local time is used only for display and for grouping slots by day; the clock and the UTC→local conversion are injectable for tests; no provider timezone exists, so none is assumed and UTC is never labelled local. (3) **Reservation creation is never retried automatically** (no idempotency key): one request per deliberate tap, duplicate taps ignored while pending, the user decides after a failure. (4) **Account scoping:** every patient provider watches the signed-in account id (`accountIdProvider`), so logout, expiry or switching rebuilds it; paged lists use an epoch so a late page or an older query's answer can never replace newer state; screen-scoped requests are cancelled on dispose. (5) **After a booking or cancellation** the list, opened details and availability are invalidated and reloaded from the backend. (6) **Errors:** localized, user-safe text chosen by the machine code; conflicts have their own messages; `404` is one generic text (no existence disclosure); server internals are never shown. (7) **Strict-but-tolerant parsing:** required fields missing or mistyped make the response unreadable (`invalid_response`); unknown statuses are kept as `unknown` and rendered; `provider_id` is read as nullable because the backend nulls it when a provider is deleted. (8) **Contract test:** the committed `docs/api/openapi.yaml` is scanned by a Dart test for every path, field and status the patient screens use.
**Consequences:** A stale slot, a double tap, a lost response or an account switch cannot produce a duplicate or foreign booking or a wrongly timed appointment; changing the API contract breaks a test rather than the app silently. Provider-side screens (11C) reuse the same primitives.

## ADR-055 — Mobile provider & facility workspace: server-decided, account-keyed, mutation-safe
**Date:** 2026-10-03
**Decision:** (1) **The server decides.** Screens appear only for accounts whose `/me` lists `reservations.manage_received`; which dashboard to open comes from `GET /dashboards/` (facility wins over doctor), never from a role label; the backend still requires a PROVIDER account with a provider profile on every call (403 → guidance). Facilities use the same availability and reservation endpoints as practitioners; no facility-wide practitioner aggregation is built because the API has no such relation. (2) **Transitions are a hint.** Buttons are chosen from the current status and start time to mirror `PROVIDER_TRANSITIONS` and its time rules; the backend decides, a refusal is shown and the record refetched. (3) **Availability is the backend's.** The app collects a service, a date and a start time (device-local), sends UTC, and shows only what the API returned; the end time, overlap and future-time checks are never computed locally. The picker conversion is the injectable `localToUtcProvider`, the inverse half of the 11B policy (no second timezone policy). (4) **Account scoping, three layers:** data families that hold one account's records are keyed by `(account, id)` (so a new account starts from loading instead of the previous account's cached value — Riverpod keeps the last value while a provider rebuilds); paginated notifiers rebuild on `accountIdProvider`; screen-local state (form input, messages, busy flags) resets through `ref.listen(accountIdProvider)`. (5) **Mutations run through one wrapper** that captures the initiating account, drops the result with `StaleSessionException` (and does not invalidate anything) if another account is signed in when the call ends, invalidates only after a successful backend answer, and never retries. (6) **One request per tap:** the shared progress button blocks duplicates, and while a transition runs the other transitions are disabled; local pickers use plain buttons (no progress state while a dialog is open). (7) **Contract tests:** the committed `docs/api/openapi.yaml` is scanned for every path, method, field, required key and enum the workspace uses. (8) **Latent 11B fix:** the patient reservation detail provider had the same Riverpod last-value behaviour and could show account A's reservation to account B while B's request was in flight; it is now keyed by account too.
**Consequences:** A late answer, a stale cache or a typed-but-unsent value of one account cannot surface under another; a wrong time zone cannot silently shift an appointment; the backend contract is pinned by tests. Profile/service editing, facility membership management and chat/notifications remain later subphases.

## ADR-057 — Mobile chat, notifications and FCM client: persistence is the truth, push is a hint, token lifecycle is account-keyed
**Date:** 2026-10-06
**Decision:** (1) **Persistence is authoritative.** The notification centre and conversations read the backend; counts come from the backend endpoints and are reloaded (not patched) after every mutation or foreground push; nothing from a push payload is stored or shown as a notification. (2) **Read semantics follow the server.** Fetching a thread does not mark it read; the thread sends one explicit cursor (`through_sequence` = highest loaded sequence) per newly observed message, never in a retry loop. Notification rows are marked by an explicit tap. (3) **Conversations start only from a reservation** (the only creation endpoint); no "new chat" UI is invented. (4) **Navigation:** Home *Explore* entries with badges (role-neutral), not the bottom bar or app chrome; routes are flat. (5) **FCM behind `PushSource`.** Firebase is initialised from `--dart-define` client identifiers (no `google-services.json`/Gradle plugin/secret); absent configuration means `DisabledPushSource` and an otherwise identical app. (6) **Token lifecycle.** A `PushRegistration` notifier is rebuilt per account (state is account-keyed); registration is the idempotent upsert and happens only with OS permission, which is re-read inside EVERY synchronisation (a token refresh or a start-up race can never register while notifications are denied/undetermined); the permission prompt is an explicit button on the notification centre; the device is unregistered before logout through a time-bounded `beforeLogoutProvider` hook. Server-side ownership is changed only through the serialised `PushOwnershipLane` — `POST /notifications/push-devices/` transfers the globally unique token to whichever account calls it and the server has no client ordering, so dropping a stale *response* is not enough: an old request still in flight could commit after the new account's and hand the token back. The app therefore routes every register/unregister through one FIFO `PushOwnershipLane`: (1) one ownership request at a time (the next starts only after the previous returned or hit its own timeout); (2) these requests use `ApiClient.postDetached`, which is NOT aborted when the session ends, so the lane really waits for the server's answer; (3) a queued registration decides at its turn which account is current and, if the account changed while a request was in flight, registers the new current account afterwards; (4) logout queues the unregister behind any in-flight registration, with the signing-out account's own bearer captured up front, so it completes even after credentials are cleared; (5) a request whose outcome the client never saw (timeout/transport error) marks the belief unknown and schedules a bounded repair registration for the current account after `pushRepairDelayProvider` (default 2 minutes, longer than any request can linger). **Guarantee and its limit:** whenever each ownership request's outcome is observed, the final owner is the current account (tested with a server-side ownership simulation). When an outcome is NOT observed, convergence relies on the repair delay exceeding the request's maximum lifetime; a strict proof under arbitrary network delay would need server-side ordering. Minimal change if that proof is wanted (NOT implemented, needs approval): register accepts an optional monotonically increasing `registration_seq` (e.g. epoch milliseconds) stored on `PushDevice` (one nullable column + migration) and ignores a registration whose value is lower than the stored one. (7) **Taps.** One `PushIntentCoordinator` (pure Dart, tested) turns a tapped or launching push into at most one validated navigation through the existing router: held while restoring, dropped on sign-out, deduplicated by message id or a short window; a notification push opens the centre because the payload has no resource id. (8) **No local-notification package and no background handler:** the system tray shows the backend's notification message and a foreground push only refreshes.
**Consequences:** A late answer, stale token callback, typed draft or old tap of account A cannot reach account B; a missed push loses nothing because the centre fetches backend state; the app builds and runs without any Firebase project. Real FCM transport needs a Firebase project's client configuration and an on-device test (not performed here).
