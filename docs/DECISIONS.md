# Architecture decisions

Append-only log. Newest at the bottom. Format: context → decision → consequences.

---

## ADR-001 — Modular monolith on Django, one container, one PostgreSQL
**Date:** 2026-09-23
**Context:** Legacy Racheeta spread logic across client apps and ad-hoc backends; cost and maintainability suffered. Owner requires low Railway cost and portability.
**Decision:** One Django project with business modules as apps. One container image serving both the API and the React build. PostgreSQL is the only stateful service. No Redis, worker, WebSocket server, search engine or PostGIS until a feature needs it.
**Consequences:** Simple operations and cheapest possible hosting. Modules must stay decoupled through clear app boundaries so that extracting one later stays possible. Insertion points for later services: cache backend (`CACHES`), `ASGI_APPLICATION`, storage backends (`STORAGES`), `INSTALLED_APPS`.

## ADR-002 — Django 5.2 LTS, Python 3.13, exact dependency pins
**Date:** 2026-09-23
**Context:** Django 6.x exists, but the project must be maintainable by rotating engineers/assistants.
**Decision:** Pin Django 5.2 LTS (supported to April 2028) and pin every dependency exactly in `requirements/*.txt` and `package-lock.json`.
**Consequences:** Predictable builds; upgrades are deliberate PRs. Revisit Django 6 after the platform is in production.

## ADR-003 — Single environment-driven settings module
**Date:** 2026-09-23
**Context:** Split `settings/dev.py` / `prod.py` files frequently drift and make it easy to run production with development settings by forgetting `DJANGO_SETTINGS_MODULE`.
**Decision:** One `config/settings.py`; behaviour switches on `DEBUG` and explicit variables. `SECRET_KEY` and `DATABASE_URL` have no defaults. `config/test_settings.py` is the only variant (fast hashing, no collectstatic).
**Consequences:** Impossible to boot without real configuration; production hardening activates automatically when `DEBUG=false`.

## ADR-004 — One `Account` model, email login, UUID primary keys
**Date:** 2026-09-23
**Context:** Legacy had multiple user types with separate identities and integer IDs leaked into clients.
**Decision:** Custom `AUTH_USER_MODEL = accounts.Account` created before any other migration. Email is the login identifier, unique case-insensitively (functional unique index on `LOWER(email)`). All domain entities use UUID v4 primary keys via `apps.core.models.BaseModel`.
**Consequences:** No username. Profiles/roles hang under the account. Public IDs are not enumerable. Composite indexes on UUIDs are slightly larger than on integers — acceptable.

## ADR-005 — Coarse primary role on the account, capabilities computed server-side
**Date:** 2026-09-23
**Context:** Many user types (doctor, nurse, hospital, pharmacy, company, real-estate…) but one identity.
**Decision:** `Account.role ∈ {PATIENT, PROVIDER, MEDICAL_COMPANY, REAL_ESTATE_SELLER, ADMIN}`. Finer typing goes into profile models (Phase 2). `/me` returns computed capability codes (`apps/accounts/roles.py`) that clients may use for UI only. `ADMIN` is never client-assignable; a DB check constraint requires `is_staff` for `ADMIN`.
**Consequences:** One place to reason about authorization. Adding a role touches `roles.py`, a migration and `PERMISSIONS.md`.

## ADR-006 — JWT with rotating, blacklisted refresh tokens
**Date:** 2026-09-23
**Context:** Web, Flutter and dashboards must share one stateless session model.
**Decision:** SimpleJWT. Access 15 min (memory), refresh 14 days (rotated on use, old token blacklisted, blacklist table in PostgreSQL). Logout blacklists the refresh token.
**Consequences:** No Redis needed for sessions. Blacklist table grows; run `flushexpiredtokens` periodically (scheduled job planned). Web stores the refresh token in `localStorage` for now — see ADR-009.

## ADR-007 — Uniform error envelope and JSON 404 under `/api/v1/`
**Date:** 2026-09-23
**Context:** Clients need one way to handle errors; DRF's default shapes vary by exception.
**Decision:** `apps.core.exceptions.api_exception_handler` wraps every DRF error as `{"error": {"code", "message", "details"?}}`. A catch-all route returns the same envelope for unknown API paths.
**Consequences:** Mobile and web share one error parser (`web/src/api/client.ts` → `ApiError`).

## ADR-008 — OpenAPI file is committed and checked in CI
**Date:** 2026-09-23
**Context:** Master plan: OpenAPI is the contract for mobile/web.
**Decision:** `docs/api/openapi.yaml` is generated by `scripts/export_openapi.sh`; CI diffs it against the code and fails when stale.
**Consequences:** Every API change is visible in review as a schema diff. Flutter/TS client generation can start from this file.

## ADR-009 — Web token storage: access in memory, refresh in localStorage (interim)
**Date:** 2026-09-23
**Context:** httpOnly-cookie refresh flows need CSRF handling and cookie-domain planning; the web app has no real pages yet.
**Decision:** Interim: refresh token in `localStorage`, access token in memory, single in-flight refresh with retry. Revisit in Phase 12 (candidate: httpOnly SameSite cookie for the refresh token + CSP).
**Consequences:** Accepted XSS exposure of the refresh token until then; no inline scripts/`dangerouslySetInnerHTML` allowed in the web app.

## ADR-010 — Django serves the React build (same origin) via WhiteNoise
**Date:** 2026-09-23
**Context:** One Railway service is the cost target.
**Decision:** Dockerfile builds `web/` and copies `dist/` into the image; `SPA_DIST_DIR` makes WhiteNoise serve assets from the URL root and a catch-all view returns `index.html` for non-API routes. In development Vite proxies `/api` and `/health` to Django, so `VITE_API_BASE_URL` stays empty everywhere.
**Consequences:** No CORS in production. If the web app is ever hosted separately (CDN), set `VITE_API_BASE_URL` and `CORS_ALLOWED_ORIGINS`; nothing else changes.

## ADR-011 — Mandatory loading pattern as shared components
**Date:** 2026-09-23
**Context:** Master plan §19: every backend-connected button/page must show loading state and block duplicate submissions.
**Decision:** `ApiActionButton`, `AsyncPage`, `LoadingOverlay`, `Spinner` and hooks `useAsyncAction` / `useAsyncData` in `web/src`. Feature code must use them instead of hand-rolled state. The Flutter app will mirror the same three components.
**Consequences:** Reviewers reject raw `<button onClick={api…}>` usage.

## ADR-012 — WSGI gunicorn now, ASGI later; migrations in the container start
**Date:** 2026-09-23
**Context:** No async views yet; Railway has no release phase.
**Decision:** Run `gunicorn config.wsgi` (2 workers). Keep `config/asgi.py`. `scripts/start.sh` runs `migrate` before serving, safe with a single replica.
**Consequences:** Switch to `uvicorn config.asgi:application` when WebSockets/async arrive. Move `migrate` to a pre-deploy step before scaling replicas.

## ADR-013 — Health endpoint does not check the database
**Date:** 2026-09-23
**Context:** Railway restarts a service whose health check fails.
**Decision:** `/health/` returns `{"status":"ok"}` if the process serves HTTP. Database problems surface as API errors and (later) monitoring, not as restart loops.
**Consequences:** Add a separate readiness/diagnostics endpoint if deeper checks are needed.

## ADR-014 — Proprietary licence, owner-assigned contributions
**Date:** 2026-09-23
**Decision:** `LICENSE` states all rights reserved by Moahaimen Talib; contributions are assigned to the owner.
**Consequences:** No open-source obligations; change only by owner decision.

## ADR-015 — Stateless HMAC tokens for password reset and email verification
**Date:** 2026-09-23
**Context:** Reset/verification links need expiring, single-use, unguessable tokens. Options: a token table with hashed values, or Django's stateless generator design.
**Decision:** Use `PasswordResetTokenGenerator` subclasses with per-purpose salts (`apps/accounts/tokens.py`). The HMAC covers a timestamp and account state (password hash / `email_verified_at` / email), so a token dies when the flow completes or the state changes. No token table.
**Consequences:** Zero storage and no cleanup job. A password reset invalidates every earlier reset link at once. Multiple verification links stay valid until one is used (accepted). Rotating `SECRET_KEY` invalidates all links (expected).

## ADR-016 — `email_verified_at` timestamp; verification does not gate features yet
**Date:** 2026-09-23
**Decision:** Replace the boolean with a nullable timestamp (data-preserving migration `accounts.0002`). Expose `email_verified` and `email_verified_at` on `/me`. No endpoint requires verification.
**Consequences:** Auditable state. Gating rules are a later, documented business decision (`PERMISSIONS.md`).

## ADR-017 — Firebase behind a verifier adapter, disabled by default
**Date:** 2026-09-23
**Context:** Owner has no Firebase credentials configured; development must not block on them.
**Decision:** `FirebaseVerifier` protocol + `DisabledVerifier` (503) + `FirebaseAdminVerifier` (lazy `firebase-admin` import, credentials file from env). Endpoint logic is fully tested with a fake verifier. Linking requires a Firebase-verified email; new accounts get an unusable password; `firebase_uid` is stored on the account.
**Consequences:** Activation is configuration only (see `AUTHENTICATION.md`). The `firebase-admin` dependency is added only when activated. A separate `SocialIdentity` table can replace `firebase_uid` if a second identity provider ever appears.

## ADR-018 — Email remains required; phone-only Firebase sign-in deferred
**Date:** 2026-09-23
**Context:** Firebase phone auth yields identities without an email, but `Account.email` is the canonical identifier.
**Decision:** The exchange rejects identities without an email (`email_required`). Supporting phone-only accounts needs a nullable email plus login/reset adjustments; decide when phone auth is actually enabled.
**Consequences:** Google sign-in works once activated; phone sign-in needs a follow-up ADR.

## ADR-019 — Email via `EMAIL_URL`; production refuses console backends
**Date:** 2026-09-23
**Decision:** Django email backend from `EMAIL_URL` (console in dev). System check `racheeta.E001` fails `manage.py check` when a console/locmem backend is configured with `DEBUG=false`. Provider choice deferred to the owner; the integration point is one variable.
**Consequences:** Tokens cannot end up in production logs by misconfiguration. CI sets a placeholder SMTP URL.

## ADR-020 — Per-request localisation of API messages
**Date:** 2026-09-23
**Decision:** `LocaleMiddleware`; clients send `Accept-Language`; the web client sends the UI language. Default `ar`.
**Consequences:** Validation messages match the UI language without client-side translation tables for backend errors.

## ADR-021 — Web session layer and route guards
**Date:** 2026-09-23
**Decision:** `react-router` (data router). One `AuthProvider` owns session state and talks to `/me`; guards (`RequireAuth`, `PublicOnly`) are the only places that check authentication; pages never read tokens. Restoration keeps tokens on non-401 failures.
**Consequences:** New protected pages are added under the `RequireAuth` group only. Feature code is reviewed against this rule.

## ADR-022 — Submit buttons are `ApiActionButton`
**Date:** 2026-09-23
**Decision:** `ApiActionButton` with `type="submit"` owns form submission (prevents native submit, works with Enter through implicit submission). Client validation failures throw `ClientValidationError`, which handlers ignore, so a failed validation never calls the backend and never shows a spinner.
**Consequences:** One loading pattern for forms and plain buttons; no `onSubmit` handlers that call the API.

## ADR-023 — One provider table, two kinds, controlled types
**Date:** 2026-09-23
**Context:** Legacy Racheeta had separate identities/tables per healthcare type. Master plan §7 asks for shared abstractions.
**Decision:** `ProviderProfile` is one table for all provider types; `ProviderType` (enum) is grouped into PRACTITIONER and FACILITY kinds. Type-specific attributes will be optional one-to-one extension tables added only when a business rule needs them. No new provider type may be added without touching the enum, migration and docs.
**Consequences:** Discovery, verification, memberships and services are written once. Extension tables must never carry authentication data.

## ADR-024 — Public discovery shows VERIFIED + visible providers only
**Date:** 2026-09-23
**Decision:** `ProviderProfile.objects.discoverable()` is the single gate for public list/detail/related lookups. Verification is admin-only; providers can request review.
**Consequences:** A fresh deployment lists nobody until administrators verify; that is the intended trust model. Ratings are absent until Phase 4 rather than faked.

## ADR-025 — Membership workflow with partial unique index
**Date:** 2026-09-23
**Decision:** `ProviderMembership` carries a status (PENDING/ACTIVE/REJECTED/ENDED) and `initiated_by`; both sides may initiate; a PostgreSQL partial unique index keeps one live row per pair while history rows remain. Full invitation UX (notifications, search-by-name) is deferred; the API foundation is complete.
**Consequences:** Phase 9 notifications can hook the transitions without schema changes.

## ADR-026 — Geography and specialties are database reference data seeded by migrations
**Date:** 2026-09-23
**Decision:** Country → Governorate → City and Specialty live in the database with stable UUIDs, bilingual names and slugs, seeded through data migrations from `seed_*.py` files. Clients fetch them from unpaginated public endpoints and never hard-code names. No PostGIS; coordinates are plain decimals.
**Consequences:** Adding a country or specialty is a migration (reviewable, reproducible). Geo search by distance is a later decision (PostGIS or bounding boxes) when the feature is scheduled.

## ADR-027 — Service prices carry a currency from an allow-list
**Date:** 2026-09-23
**Decision:** `ServiceOffering.price` (decimal ≥ 0) + `currency` (default IQD; allowed list `settings.RACHEETA["CURRENCIES"]`). No FX, no formatting on the server.
**Consequences:** Pricing for reservations (Phase 3) and payments (Phase 8) reference offerings rather than free text.
